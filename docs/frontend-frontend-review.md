**Scope:** All `.ts` / `.tsx` files in `frontend/src/`, plus `tsconfig.json`, `next.config.js`, `globals.css`, `middleware.ts`  
**Date:** 2026-06-29

## 1. SECURITY ISSUES

### 1.1 JWT Auth in Middleware — Decodes Untrusted Token Server-Side Without Verification [HIGH]
**Files:** `middleware.ts`

```ts
const rawPayload = Buffer.from(token.split('.')[1], 'base64url').toString();
const claims = JSON.parse(rawPayload) as { role?: string };
```

**Problem:** The Next.js middleware decodes the JWT payload by base64-decoding it but does **not** verify the signature or HMAC. An attacker can craft any token payload (e.g., `{ "role": "admin" }`) and the middleware will trust it. This means the entire server-side role-based access control on `/dashboard/admin` is bypassable.

**Fix:** Use a proper JWT verification library (e.g., `jsonwebtoken` or NextAuth's built-in verification) and verify the token signature using the same secret used to sign tokens. Alternatively, verify the token against the backend at this point.

### 1.2 Multiple `window.confirm` / `window.prompt` Usable for XSS Indirectly [MEDIUM]
**Files:** `chat-sidebar.tsx`, `folder-item.tsx`, `knowledge-sidebar.tsx`, `document-list.tsx`, `answer.tsx`, and others

**Problem:** `window.confirm` and `window.prompt` are used throughout for destructive actions (delete, rename). These are modal blocking calls that cannot be styled and are easily bypassed via API calls — the real enforcement must be server-side.

**Fix:** Replace with the project's existing `<Dialog>` component for consistency and accessibility. Server-side validation is already present for delete/rename endpoints.

### 1.3 `dangerouslySetInnerHTML` in `mermaid-diagram.tsx` [MEDIUM]
**File:** `frontend/src/components/chat/mermaid-diagram.tsx`

```ts
dangerouslySetInnerHTML={{ __html: svg }}
```

**Problem:** The SVG string is generated by the mermaid library from user-provided code in the markdown stream. If the backend's streaming response is compromised, arbitrary HTML/JS could be injected.

**Fix:** Sanitize the SVG using a library like `DOMPurify` before rendering, or use mermaid's `render` API which already sanitizes.

### 1.4 `atob` Decoding in `auth.ts` — Weak Error Handling [LOW]
**File:** `frontend/src/lib/auth.ts`

```ts
const decoded = atob(payload.replace(/-/g, '+').replace(/_/g, '/'));
```

**Problem:** `atob` throws on invalid input but the error is only logged to `console.error`. In `middleware.ts`, the equivalent base64url decoding uses a raw `Buffer.from(...).toString()` with no URL-safe character handling (no `-` → `+` / `_` → `/` conversion), which will produce garbage for standard JWTs.

**Fix:** Ensure consistent base64url decoding everywhere, or use a proper JWT library.

### 1.5 Password Validation Bypass on Admin User Creation [MEDIUM]
**Files:** `admin/users/page.tsx`, `admin/data-sources/page.tsx`

```tsx
// Create dialog: placeholder says "Minimum 1 character"
<Input placeholder="Minimum 1 character" type="password" value={createForm.password} ... />
```

**Problem:** The admin user creation dialog accepts passwords as short as 1 character. While `validatePasswordStrength` exists, it is only called in `handleChangePassword` (for the change-password flow), not in `handleCreate`. A super_admin could create a user with a 1-character password.

**Fix:** Call `validatePasswordStrength` in `handleCreate` before posting.

### 1.6 Server-Side Token Decoding Without Base64url Conversion in Middleware [HIGH]
**File:** `middleware.ts`

```ts
const rawPayload = Buffer.from(token.split('.')[1], 'base64url').toString();
```

While `base64url` encoding is specified, the JWT spec says the payload is base64url-encoded, but this code passes the raw middle segment (which may contain URL-unsafe chars like `-` and `_`) to `Buffer.from(..., 'base64url')`. Node's `base64url` encoding handles this, but **the token is never verified** — see 1.1. This is a duplicate of the same issue but worth emphasizing: this is the single most critical security finding in the frontend.

## 4. MISSING TYPES & `any` USAGE

### 4.1 `FetchOptions.data?: any` [HIGH]
**File:** `frontend/src/lib/api.ts`

```ts
interface FetchOptions extends Omit<RequestInit, 'body' | 'headers'> {
  data?: any;
```

Every API call's payload is untyped. The `api.post`, `api.patch`, `api.put` signatures all use `any`:

```ts
post: (url: string, data?: any, options?) => fetchApi(url, { ...options, method: 'POST', data })
```

**Impact:** No compile-time safety on API payloads. Typos in field names pass silently.

**Fix:** Generic API helper: `post<TReq, TResp>(url, data: TReq, options?) => Promise<TResp>`

### 4.2 `ContextDoc.metadata: Record<string, any>` [MEDIUM]
**Files:** `answer.tsx`, `agent-timeline.tsx`, `chat/[id]/page.tsx`

The metadata field on context documents is untyped. The code accesses `citation.metadata.kb_id`, `citation.metadata.document_id`, `d.context_lines`, `d.coverage_lines`, etc. with no TypeScript enforcement.

### 4.3 `api.get()` return type is `any` [MEDIUM]
**File:** `frontend/src/lib/api.ts`

```ts
const data: Folder[] = await api.get("/api/folders");
```

Every caller must manually cast the return type. The API helper should return typed results.

### 4.4 `AgentStep` index signature `[key: string]: unknown` [LOW]
**File:** `frontend/src/components/chat/[id]/page.tsx`

```ts
interface AgentStep {
  node: string;
  latency_ms: number;
  status: string;
  [key: string]: unknown;
}
```

This makes the type essentially `any` while also listing known fields, providing false confidence.

### 4.5 Error Casting Everywhere [MEDIUM]
**Files:** Multiple admin pages

```ts
(err as { message?: string }).message ?? 'Failed to load data'
(err as ApiError).message ?? 'Failed to save data store'
```

Consistent error typing would reduce these repetitive type assertions.

## 5. PERFORMANCE ANTI-PATTERNS

### 5.1 `DocumentUploadSteps` — Inline `onDrop` Creates New Closure on Every Render [LOW]
**File:** `frontend/src/components/knowledge-base/document-upload-steps.tsx`

```ts
const onDrop = useCallback((acceptedFiles: File[]) => { ... }, []);
```

This is actually correctly memoized. No issue here — corrected.

### 5.2 `Answer` Component — Citations Fetched Per-Render During Streaming [MEDIUM]
**File:** `frontend/src/components/chat/answer.tsx`

The `useEffect` that fetches citation info runs every time `debouncedCitations` changes:

```ts
useEffect(() => {
  const fetchCitationInfo = async () => {
    for (const citation of debouncedCitations) { ... }
  };
  if (debouncedCitations.length > 0) {
    fetchCitationInfo();
  }
}, [debouncedCitations]);
```

During streaming, `citations` updates frequently. The debounced value (300ms) means this effect fires repeatedly, potentially re-fetching the same citation info many times.

**Fix:** Track which citation keys have already been fetched and skip re-fetching.

### 5.3 `ChatSidebar` — `renderChatItem` Creates New Function Per Render [MEDIUM]
**File:** `frontend/src/components/chat/chat-sidebar.tsx`

```ts
const renderChatItem = (chat: ...) => { ... };
```

This function is recreated on every render and called in JSX, meaning every chat item is re-rendered whenever the sidebar re-renders (e.g., on search/query changes).

**Fix:** Wrap in `useCallback` or extract to a separate component.

### 5.4 `processedMessages` useMemo Calls `.map()` on Every Memoization [MEDIUM]
**File:** `frontend/src/components/chat/[id]/page.tsx`

```ts
const processedMessages = useMemo(() => {
  return messages.map((message) => { ... });
}, [messages]);
```

The `markdownParse` function is called for every assistant message on every render where `messages` changes (which is every new message, every streaming chunk). The regex-based citation parsing is relatively expensive.

**Fix:** Parse citations lazily or cache parsed results per message ID.

### 5.5 Multiple `useEffect` for Recovery Status Polling [MEDIUM]
**File:** `frontend/src/app/dashboard/admin/data-sources/page.tsx`

Three separate `useEffect` hooks handle polling:
1. Recovery status polling (every 5s)
2. Datastore list refresh when recovery completes (every 2s)
3. General polling for processing/scanning state (2-5s based on state)

These run independently and can hammer the backend simultaneously.

**Fix:** Consolidate into a single polling hook with coordinated intervals.

## 8. INCONSISTENT PATTERNS

### 8.1 Error Handling Style [MEDIUM]
Inconsistent patterns across files:

| Pattern | Example |
|---------|---------|
| `err instanceof ApiError` check | `answer.tsx`, `api.ts` |
| `(err as { message?: string }).message` | `admin/users/page.tsx`, `admin/orgs/page.tsx` |
| `(err as ApiError).message` | `admin/data-sources/page.tsx` |
| `error instanceof Error ? error.message : "default"` | `chat/[id]/page.tsx` |
| Silent `.catch(() => {})` | `chat-context.tsx`, `knowledge-context.tsx` |

**Fix:** Define a consistent error handling pattern and use it everywhere. Consider a `handleApiError()` utility.

### 8.2 Token Storage — Cookies vs localStorage [MEDIUM]
**Files:** Login: `document.cookie = \`token=${data.access_token}\`...` (sets cookie) but `localStorage.getItem("token")` reads from localStorage.

The middleware reads from `request.cookies.get('token')` but client-side code reads from `localStorage.getItem("token")`. If the token is in localStorage, the middleware won't see it. The cookie is set with `SameSite=Lax` and no `Secure` flag, and no `httpOnly` flag — meaning it's readable by JS AND sendable by the browser, creating a confusion point.

### 8.3 `useEffect` eslint-disable Comments [MEDIUM]
**Files:** Multiple files

```ts
// eslint-disable-next-line react-hooks/exhaustive-deps
}, [knowledgeBaseId, refreshKey]);
```

These suppress the exhaustive-deps rule to avoid capturing stale closures. The proper fix is to use refs for all mutable values accessed inside effects.

### 8.4 State Initialization: `useState("")` vs `useState(null)` vs `undefined` [LOW]
Different files use different patterns for optional string state:
- `useState<string | null>(null)` in `dashboard/admin/page.tsx`

- `useState(undefined)` in some places

## 10. CONFIG FILE ISSUES

### 10.1 `next.config.js` — Backend URL From `process.env` at Build Time [MEDIUM]
**File:** `frontend/next.config.js`

```ts
destination: `${process.env.BACKEND_URL || "http://backend:8000"}/api/:path*`
```

The rewrite destination is determined at **build time**, not runtime. This means the Docker image must be rebuilt for every environment change. If `BACKEND_URL` is set at container runtime, it won't take effect.

**Fix:** Use middleware-based API proxying (which already exists in `middleware.ts`) or Next.js middleware rewrites that evaluate at request time.

### 10.2 `tsconfig.json` — `isolatedModules: true` With Non-Module File Risk [LOW]
**File:** `frontend/tsconfig.json`

```json
"isolatedModules": true,
```

This requires every file to be a valid module (have at least one import/export). The `globals.css` is referenced in `include` but is a CSS file — that's fine. No actual issue.

## 12. TOP PRIORITY RECOMMENDATIONS

1. **Fix JWT verification in `middleware.ts`** — This is the single most critical issue. The middleware trusts unverified JWT payloads for admin access.
2. **Add types to `api.ts`** — Replace `any` with generics so all API calls are type-checked.
3. **Extract shared layout components** — Consolidate logout, password dialog, and header into a single shared component used by all three layouts.
4. **Centralize token access** — Create `getToken()` in `lib/auth.ts` and replace all `localStorage.getItem("token")` calls with it.
5. **Replace `window.confirm`/`prompt` with `<Dialog>`** — Consistent UX, better accessibility.
6. **Externalize hardcoded Chinese strings in `test-retrieval/[id]/page.tsx`** — Or remove if the page is unused.
